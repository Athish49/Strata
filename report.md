# Company Documents Pipeline — Decoupling Audit

**Scope:** company-documents data and pipeline code only (ingestion, storage, clause/citation/parameter extraction, S1-vs-S2 compliance linkage to regulations). Federal/state regulatory ingestion code (`app/regulatory/`) and unrelated application features were explicitly **not** audited, per the brief — they're only mentioned where company-doc code reads from them.

**Method:** four parallel read-only sub-agents (synthetic-generation tree, production pipeline + scripts + migrations, frontend fixtures, docs/git-history) plus direct live verification by this session against the running Neon database, Qdrant cluster, and Cloudflare R2 bucket (all read-only `SELECT`s / listings, zero writes). Every claim below is tagged:
- **[live]** — a number or fact read directly from the running Neon/Qdrant/R2 during this session
- **[code]** — confirmed by direct code/grep read (by this session or a sub-agent), not executed
- **[test-run]** — confirmed by actually running a test/suite this session
- **[git]** — recovered from git history (`git show`), read-only, nothing restored

No code was changed. No files were deleted. The two companion documents at the repo root (`live_ingestion_architecture.md`, `tables_and_connections.md`) are new and give the full architecture/data picture this report's verdicts rest on — this file is the audit + action list on top of them.

## Addendum — two findings from a second verification pass, both more significant than anything in the original action list

Before this report's action list is implemented, two more live-code findings need to sit above everything else below. The first is a confirmed architectural limitation of the live v2 pipeline. The second is an open question about whether most of the "live, verified" data this report leaned on actually came from that pipeline at all. **Read both before trusting any "confirmed live" claim elsewhere in this document about the 12 non-register documents specifically** — the 3 register documents' data is on much firmer footing and is what finding 1 is actually proven against.

### Finding 1 (confirmed by code; consistent with, though not standing alone proven by, the cleanest live data available): the v2 pipeline cannot create cross-document links for 5 of its 6 link types

`app/company_ingest/service.py:663-664` calls `resolve_references(units, known_doc_ids, ctx)` and `find_restates_links(units, links, ctx)`, where `units` is built fresh inside `ingest_document` — which, per its own docstring, "ingests exactly ONE version of ONE document." Every index-building helper in `resolve_refs.py` (`_build_clause_index`, `_build_rule_index`, `_build_form_index`, `_build_series_index`, `_build_obligation_index`, `_build_doc_index`) and `restates.py`'s parameter-signature grouping takes only that in-memory `units` list as input — confirmed by reading every one of their signatures, not just the clause index. **This means all of `restates`, `references_clause`, `references_tariff`, `references_form`, `references_record_series`, and `references_obligation` are single-document-scoped in the current architecture — not just `references_clause`**, correcting an earlier, narrower pass of this finding.

The one exception, `references_doc` (whole-document references), is checked against `known_doc_ids`, separately populated from a real `SELECT doc_id FROM company.company_documents` query (`app/api/company/versions.py:219-221`) — so it's *structurally* capable of cross-document resolution. **Whether it actually works for real documents is unconfirmed, not proven**, for two reasons: it has zero live link rows from the one source of unambiguously-fresh v2 data (the register documents — see below); and no code anywhere in `enrich/references.py` or `resolve_refs.py` translates between a document's human-readable `doc_number` (e.g. "RPL-TAR-GRR-012," the form prose would actually reference a document by) and its internal `doc_id` (e.g. "DOC-000007") — confirmed by grep, zero hits. The 125 live `references_doc` rows that do exist are all on the 12 non-register documents, already in `DOC-...` form, which is consistent with having been re-keyed during whatever carryover produced that data (finding 2) rather than evidence the live mechanism resolves a real `doc_number`-style hint today.

**The gap is visible, though not provable beyond doubt, in the one part of the live data that's most likely a fresh v2 run.** The 3 register documents (`DOC-000002`, `DOC-000004`, `DOC-000006`) show every sign of a genuine, fresh-today v2 ingest (full `report.json` stats, real `llm_extractions` cache rows, real R2 derived snapshots), though finding 2 means even this inference carries some uncertainty. Their `clause_links` contain **zero cross-document links of any kind** — live query, confirmed — despite their own `report.json` recording 68 `unresolved_ref` warnings pointing at clauses in other documents (`RPL-TAR-GRR-012`, `RPL-DO-PLN-002`, `RPL-MTR-PGM-001`, `RPL-CS-PRO-004`, etc.). This is consistent with the code-level finding above; it is corroborating evidence, not an independent proof, since the register documents' hints also use the `RPL-*` doc_number format that no code path translates.

**Live-impact claim, scoped precisely:** `app/engine/candidates.py`'s `LINK_TYPES` constant — the set of link types it actually reads for candidate propagation — is `("references_clause", "references_obligation", "references_record_series", "references_tariff", "references_form")`. **It does not include `restates`.** So the confirmed engine-impact is: a clause that *references* content in a different document, where that content is directly hit by a regulation change, is not propagated as a candidate today — for new uploads through the real v2 API. `restates` links are confirmed cross-document-incapable too, but this audit found no evidence they feed the engine at all; their only confirmed purpose is the clause-relationship data itself. This needs its own design decision (a cross-document reconciliation pass — on every upload? a periodic job? triggered at promotion? and resolving the `doc_number`↔`doc_id` translation gap either way) before a fix — see `implementation_plan.md` task 1.0.

### Finding 2 (evidence strong, root cause not determined): the "12 prose documents'" current Neon data may not actually be v2 pipeline output

What first looked like "stage 5/9 silently failed for 12 documents" is now better described as: **the clause-level data for all 12 prose documents matches the pre-cutover (v1-era) snapshot exactly, including cross-document links the current v2 architecture cannot produce** — which is hard to explain as a fresh, genuine run of today's `service.py`, despite `ingest_jobs`/`ingest_runs` recording a `'succeeded'` run for each, timestamped today.

**The evidence, concretely:**
- Every one of the 12 prose documents' current clause count matches `supplement_docs/CompanyData_Pipeline/company_data_storage.md`'s pre-cutover per-document table **exactly**, including the register-split sums: `RPL-CMP-REG-001` = 155 = `DOC-000001`(85) + `DOC-000002`(70); `RPL-REG-CAL-2025` = 84 = `DOC-000003`(36) + `DOC-000004`(48); `RPL-LEG-RRS-001` = 173 = `DOC-000005`(87) + `DOC-000006`(86); and all 9 standalone prose documents match their old counts digit-for-digit (331, 277, 248, 237, 228, 174, 147, 144, 136).
- The 12 prose documents' `clause_links` **contain real cross-document links** — `references_clause` (29 cross-doc), `references_obligation` (73, all cross-doc), `references_record_series` (232, all cross-doc), `references_tariff` (111 cross-doc), `restates` (628 cross-doc) — live query, confirmed. Given finding 1's airtight proof that today's `service.py` architecture **cannot** produce a cross-document link from a single-document ingest call, this data could not have been produced by a fresh run of the current pipeline. It is consistent with being carried over from the old whole-corpus batch pipeline (which could produce cross-document links naturally) and re-keyed onto the new `DOC-00000N` scheme.
- No script, migration, or any other code in the current tree or git history writes directly to `company.clauses` other than `app/company_ingest/store/neon.py` (checked via `git log --all -S "INSERT INTO company.clauses"` and a repo-wide grep) — so if this is a rekey, it most likely went through a real (if perhaps abbreviated or `reuse.py`-assisted) call into `service.py`/`neon.py`, not a separate ad-hoc script. This audit could not pin down the exact mechanism.
- The 3 register documents show the opposite pattern on every one of these checks: fully populated `report.json` stats, real `llm_extractions` rows, a real R2 derived snapshot, and **zero** cross-document links despite needing some — consistent with being genuinely, freshly ingested through today's real (and architecturally limited) pipeline.

**A further check, found since the paragraph above was first written — read it precisely, it confirms less than it might look like at first:** R2 still holds an orphaned pre-cutover snapshot at `derived/RPL-CS-PRO-004/v1/clauses.jsonl` (237 clauses, matching `DOC-000008`'s current count exactly). Its per-clause `text_sha256` was compared against `DOC-000008`'s current Neon rows for 4 `local_id`s: `1.2` and `1.3` matched exactly; `1.1` and `2.1` did **not** — both mismatches are because the *current* row has an empty `text_raw` (hashing to the well-known SHA-256 of `""`) where the v1 snapshot had real, non-empty text. **A hash match only proves the two rows have the same source text** — exactly what you'd also get from a deterministic re-parse of an unchanged `.md` file, not only from a literal copy — so on its own this doesn't distinguish "copied" from "freshly re-parsed from the same unchanged source." It does not, by itself, settle finding 2; the cross-document-links evidence and the `is_citation_fragment` NULL/set split (both below) are what actually carry that conclusion, because the current v2 architecture provably cannot produce the links finding 1 shows these documents have, regardless of how the text itself got there.

**A separate, new, smaller finding from this same check:** checking the mismatch systematically (not just the 2 spot-checked clauses) found **274 clauses across 6 of the 12 prose documents** (`DOC-000008`: 29, `DOC-000010`: 83, `DOC-000012`: 29, `DOC-000013`: 60, `DOC-000014`: 37, `DOC-000015`: 36 — confirmed live, zero in the other 6 prose docs and zero in any register document) whose current `text_raw` is **empty**, where the surviving v1 snapshot shows real (if sometimes short, e.g. a bare section heading) content for the same `local_id`. This is a genuine discrepancy between the two states, not resolved by this audit — it's folded into `implementation_plan.md` task 1.2 as an additional data point, since it bears on the same provenance question and on whether `text_raw`-dependent features (anything quoting or re-verifying clause text) see degraded content for these 274 clauses specifically.

**What this means, stated carefully:** every other "confirmed live" claim in this report and its companions about **structure** (tables exist, schema is right, FKs hold, R2 raw bytes exist for all 15) stands independently of the provenance question and is unaffected. But claims specifically about **these 12 documents' enrichment completeness** should be read as "describes what's in the database today," not "proves the v2 pipeline correctly produces this from scratch" — only the 3 register documents prove that, and the carryover conclusion for the 12 others rests on the links/flag evidence, not the hash check alone.

**Do not re-ingest or re-upload any of these 12 documents in production before task 1.2 (in `implementation_plan.md`) resolves this.** Doing so would run them through the real, architecturally-limited pipeline and **silently replace their currently-present cross-document links with none at all** — turning a data-provenance question into an actual, irreversible-without-a-backup data loss.

This doesn't block anything else in this report's action list — none of the Phase 1–5 tasks below depend on resolving either finding — but both now sit above the `is_citation_fragment` and stage-5/9 framing as the highest-priority open items, because they bear on whether the live data this whole audit verified against is representative of what the real pipeline actually does. See `implementation_plan.md` tasks 1.0 and 1.2.

## Executive summary

The decoupling the brief asks for — get company-document data and its link to federal/state compliance out of CSVs/markdown and into real database tables — **was already planned in detail and almost entirely implemented**, by an earlier effort whose design docs (`TDD.md`, `architecture.md`, `plan_mode.md`) were committed, then deleted from the working tree **[git]**. Recovered copies state the goal explicitly: *"`backend/synthetic/` can be removed with no effect on the running application. CI-enforced."* That CI enforcement is real and currently green **[test-run]**: `tests/engine/test_barrier.py` (9 tests) scans all of `app/` and `scripts/` for any reference to `synthetic/`, `corpus/`, the old `app/company` path, or hardcoded `RPL-`/`IAC`/`CFR` identifiers, and fails the build if found.

Across all four audits, **zero** production code paths were found reading a local CSV/markdown/JSON file as a data source for company documents, clauses, citations, parameters, or compliance linkage **[code]**. All of that genuinely lives in Neon + Qdrant + R2 today — structurally confirmed by live counts **[live]**, though the addendum above means "structurally confirmed" and "proven to be fresh v2 output" aren't the same claim for 12 of the 15 documents.

What remains below is not "undo the hardcoding" — the addendum's two findings are the real top priority (see `implementation_plan.md` tasks 1.0 and 1.2); everything numbered here is the original action list, still valid and independent of those:
1. **Physically delete** the now-fully-decoupled `backend/synthetic/` tree, `backend/tests/synthetic/`, and `tools/offline_eval/` (~9.2 MB, 125+ files) — but only after the five small preconditions below, because a few things quietly ride on that tree's presence.
2. **A column that's unwired at the write end — and, on closer reading, dead at every read end too.** `is_citation_fragment` is never set by the live ingest pipeline (confirmed: the 3 register documents' 1,766 fresh-v2 parameter rows are 100% NULL). But checking all 3 places that read it (`app/engine/candidates.py:98`, `app/engine/rules.py:105`, `app/engine/judge.py:384`) shows the column currently **changes no engine output at all**: `is_citation_fragment` can only ever be `True` when `kind='number' AND unit IS NULL` (by its own rule), and both `candidates.py`'s SQL filter and `rules.py`'s `_eligible()` already independently exclude every row matching `kind='number' AND unit IS NULL` via a *separate* condition in the same filter — so the `is_citation_fragment` check never changes which rows pass, provably, by the boolean logic alone. `judge.py` only selects the column into a row dict; nothing downstream filters on it. **This demotes the finding from "active correctness gap, wire it in" to "unwired and currently inert — worth a product decision, not an automatic fix."** See `implementation_plan.md` tasks 3.4/3.5, now optional, with a cheaper alternative (delete the column and the script) offered alongside wiring it in. The original framing of a second gap here — "stages 5/5b/9 incomplete for 12 prose documents" — turned out, on deeper investigation, to likely be the addendum's finding 2 instead (those documents' data may not be fresh v2 output at all, not merely missing one stage of it); see the addendum, not this list, for that one. A third, related question (citation re-resolution after regulatory KB updates) was investigated live and found to have **no active gap today** — demoted to an open product question, not a fix item.
3. **Fix stale documentation** that still describes a dead v1 entrypoint and wrong live-state claims.
4. **Resolve a couple of loose ends** (orphaned migration backup tables, triplicated vertical taxonomy) left over from other recent work.

### ⚠️ Flag found during verification, unrelated to synthetic-data decoupling but worth fixing with care

`backend/.env`'s `R2_ENDPOINT` carries a trailing `/strata` (the bucket name) that, combined with the boto3 client's `Bucket="strata"` parameter on every call, means **every object the app has ever written physically lives one path segment deeper** (`strata/company/...`) than the clean key (`company/...`) stored in Neon's own `source_r2_key` column. This is invisible to the running app (same misconfigured endpoint used for both writes and reads, so it cancels out), but **"fixing" `R2_ENDPOINT` without a key-migration plan would make every existing R2 object unreachable** at the key the app expects — breaking the ingest-job retry path and any future raw-document download. Not part of the company-docs decoupling task, but surfaced by this audit's live verification and worth a deliberate fix, not an accidental one. Full detail in `tables_and_connections.md` §7 (repo root).
